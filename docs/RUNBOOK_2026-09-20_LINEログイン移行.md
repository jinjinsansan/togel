## 0. なぜやるのか（1段落）

いまLINE側とWeb側は別々の人として扱われています。`line_users`（LINE ID・診断結果・配信先）と
`users` / `auth.users`（Supabaseのアカウント）は別のテーブルで、繋がっていません。
LINEで診断した人の結果はWebのマイページに出ず、Webで進めた攻略盤はLINEから開くと空です。
週1配信で盤を進める設計は、配信先と盤が同じ人のものだと言えて初めて成立します。
LINEログインはそこを繋ぎます。外部ブラウザ回避は副次的な効果です。

---

## 1. 🔴 不可逆な前提（ここを間違えるとやり直せません）

LINEのユーザーIDは **プロバイダー単位** で発行されます。

- 同じプロバイダー配下なら、Messaging APIチャネルとLINE Loginチャネルで **同じユーザーIDが返ります**
- 別プロバイダーだと **別の値** になり、同一人物だと判定する手段がありません
- **チャネルは、作成後にプロバイダーを移せません**

つまり LINE Loginチャネルを既存のMessaging APIチャネルと違うプロバイダーに作ると、
`line_users.user_id` を埋める設計が成立せず、**作り直しも効きません。**

出典: https://developers.line.biz/en/docs/messaging-api/getting-user-ids/

> **最初にやること**: LINE Developers Console を開き、いま使っている **Messaging APIチャネルが
> どのプロバイダーに属しているか** を確認する。LINE Loginチャネルは **同じプロバイダー** に作る。

## 3. 手順A: LINE Loginチャネルを作る

LINE Developers Console で操作します。

1. §1で確認した **Messaging APIチャネルと同じプロバイダー** を開く
2. 「新規チャネル作成」→ **LINE Login** を選ぶ
3. チャネル基本情報を入力する（アプリ名・説明・アイコン等）
4. **スコープ** に `openid` と `profile` を入れる
   - `openid` が無いと ID トークンが取れません。LIFF の `liff.getIDToken()` も null を返します
     （出典: https://developers.line.biz/en/reference/liff/ ）
5. **`email` スコープについて** — 使うには LINE Developers Console での **申請** が必要です
   （用途を説明する書類の提出が要る）。
   - 申請する場合: 承認後に `email` をスコープへ追加する
   - 申請しない場合: §4-4 で Supabase 側を `email_optional: true` にする必要がある
   - **どちらにするかは §2-4 の判断**。申請の可否と所要期間はこちらでは分かりません
6. **コールバックURL** を登録する
   - 登録する値は §4-2 で Supabase の作成フォームに表示される **読み取り専用のURL** をそのまま使います
   - 🔴 **URLを推測して先に入れないでください。** Supabase のドキュメントはこの値の形式を明記して
     おらず、「作成フォームに表示される」としか書かれていません。表示された値をコピーしてください
7. チャネルID と チャネルシークレット を控える（§4で使う）

## 4. 手順B: Supabase にカスタムOIDCプロバイダを登録する

LINE は Supabase の組み込みプロバイダには含まれていませんが、**Custom OAuth/OIDC Providers**
として登録できます。LINE は OIDC 準拠で、discovery document を公開しています（実際に取得して確認済み）。

```
issuer:             https://access.line.me
userinfo_endpoint:  https://api.line.me/oauth2/v2.1/userinfo
jwks_uri:           https://api.line.me/oauth2/v2.1/certs
scopes_supported:   openid / profile / email
id_token_signing_alg: ES256    code_challenge_methods: S256
```

1. Supabase Dashboard → Authentication → Providers → カスタムプロバイダの追加
2. フォームに表示される **コールバックURL を控える**（§3-6 でLINE側に登録する値）
3. **OIDC モード** を選び、以下を入れる
   | 項目 | 値 |
   |---|---|
   | `identifier` | `custom:line`（`custom:` で始まる必要がある） |
   | `issuer` | `https://access.line.me` |
   | `client_id` | LINE Loginチャネルの **チャネルID** |
   | `client_secret` | LINE Loginチャネルの **チャネルシークレット** |
   | `scopes` | `openid profile`（`email` を申請・承認した場合はそれも） |
4. `email` を申請していない場合は **`email_optional: true`** にする
   - Supabase はカスタムプロバイダに対し、既定でメールアドレスの返却を要求します
   - これを外さないとログインが通りません
5. LIFF からも入れるようにする場合は **`acceptable_client_ids`** に、LIFF が使うチャネルIDを入れる
   - Web の `signInWithOAuth` は先頭のIDを使い、`signInWithIdToken` は一覧のどれでも受け付けます

出典: https://supabase.com/docs/guides/auth/custom-oauth-providers

## 5. 手順C: このリポジトリ側の実装

🔴 **未実装です。** 採用が決まってから着手します。ここでは「何を触ることになるか」だけ示します。

| 対象 | やること |
|---|---|
| `src/components/auth/login-button.tsx` | `provider: "custom:line"` のボタンを足す。Googleは残す（既存8人の経路） |
| LIFF（`src/lib/line/use-liff.ts` 周辺） | `liff.getIDToken()` → `supabase.auth.signInWithIdToken()`。リダイレクトが要りません |
| `src/app/auth/callback/route.ts` | ログイン成立後に `line_users.user_id = users.id` を書く |
| 新規マイグレーション | 攻略盤の到達（visited）を置くテーブル。**`created_at` は持たない**（下記） |

**`created_at` を持たない理由**（決定済み）:
- 1人あたりの行数は最大15〜25で構造的に有界。古い行を消す運用が要らない
- 削除要求は `user_id` で消せる。日時は要らない
- 残る用途は「何日開いていないか」の計算だけで、それは作らないと決めた督促・ストリークの材料そのもの
- 列が無ければ、後から誰かがストリークを作るにはマイグレーションが要る。目に見える行為になる

**移行は和集合で足ります。** visited は順序も日時も持たない集合なので、端末Aと端末Bの集合を
足すだけで正しくなります。競合も、どちらを勝たせるかの判断も発生しません。

盤の定義（`selfTypeId` / `plan` / 相手のtypeIds）は **サーバに持つ必要がありません**。
診断結果から再構成でき、LINE側は `line_users.diagnosis_result` に保存済みです。
再構成できないのは visited だけです。

## 6. 手順D: 既存8人のリンク（手作業）

Googleでログイン済みの既存ユーザーは、LINEログインすると **別のアカウントになります**。
Supabase 上では別の `auth.users` レコードです。

自動で繋ぐ手がかりは同一メールアドレスですが、`email` スコープを申請していない場合は
**メールが取れないため手がかりがありません**。

- 対象は8人。手作業で対応できる規模です
- 🔴 **どの Google アカウントとどの LINE アカウントが同一人物かは、こちらには分かりません。**
  §2-5 の通りオーナーの確認が要ります
- 対応表が揃ったら、`line_users.user_id` に既存の `users.id` を書きます
- 🔴 **この手順の具体的な操作は、実際に1件繋いでみるまで確定できません。**
  Supabase のドキュメントは、カスタムプロバイダでの identity linking について明示していません。
  最初の1件は検証として扱い、成功を確認してから残りを進めてください

## 7. 検証手順

**実施する時点が2つに分かれます。** 7件を一度に実施することはできません。

### 7-A. 実装前に行う検証（§4の直後・§5の実装より前）

ここが通らなければ設計ごと変わります。実装に進む前に必ず確認してください。

1. **IDが一致するか**（最重要・§1の前提の実地確認）
   LINEログインを1回通し、得られた `sub` が、その人の既存 `line_users.line_user_id` と
   **同じ値か** を確認する。違えばプロバイダーの構成が想定と違うので、そこで止める

   🔴 **試すアカウントを間違えないでください。** この検証は照合相手が要るので、
   **既に `line_users` に行があるLINEアカウント**——つまり、これまでにLINE公式アカウントを
   友だち追加して使ったことがあるアカウント——で実施してください。
   登録の無いアカウントで試すと `sub` が返るだけで、**「一致しない」のか「照合相手が無い」のかを
   区別できません。**
   （`line_users` に現在何行あるか、どのアカウントが入っているかは、こちらでは確認できません。
   §9-B-9 を参照）

### 7-B. 実装後に行う検証（§5の実装が済んでから）

上から順に、1つずつ確認してください。前が通らないまま次に進まないこと。

2. **Webでログインできるか** — 通常ブラウザで `custom:line` からログイン → セッションが立つ
3. **LINE内ブラウザでログインできるか** — LINEのトークからリンクを開き、外部ブラウザに
   切り替わらずにログインが完了すること（Googleと違い、相手が LINE 自身なので通るはず）
4. **LIFF内でログインできるか** — 画面遷移なしでセッションが立つこと
5. **紐付いたか** — `line_users.user_id` が埋まっていること
6. **盤が繋がったか** — 別のブラウザで開いても、同じ visited が見えること
7. **既存8人が壊れていないか** — Googleでのログインが従来どおり通り、マイページが出ること

## 8. 失敗したときの戻し方

| 失敗 | 戻し方 |
|---|---|
| `sub` が `line_user_id` と一致しない | **先に進まない。** プロバイダーの構成を確認する。チャネルは移せないので、構成が違えば設計の作り直しになる。この時点なら実装前なので損失は小さい |
| ログインが通らない（`email_optional` 未設定など） | Supabase側の設定を直す。ユーザーデータには影響しない |
| LINEログインを取りやめる | Supabase 側でカスタムプロバイダを無効化し、ログインボタンから `custom:line` を外す。Googleの経路は触っていないので残る |
| 紐付けを間違えた（別人を繋いだ） | `line_users.user_id` を NULL に戻す。この列は `ON DELETE SET NULL` の外部キーで、**元々全行NULL**なので、NULLが正常な状態 |

**取り返しがつかないのは §1 のプロバイダー選択だけです。** それ以外は戻せます。

## 10. 実行順序（まとめ）

```
オーナーがプロバイダー構成を確認（§2-1）
  └ 同じプロバイダーに LINE Loginチャネルを作成（§3）
      └ Supabase にカスタムOIDCプロバイダを登録（§4）
          └ 実装前の検証「subが一致するか」（§7-A）  ← ここで止まる可能性がある
              └ 実装（§5）
                  └ 実装後の検証（§7-B）
                      └ 既存8人のリンク（§6）… 最初の1件は検証として扱う
```

実装（§5）を先に始めないでください。§7-A が通らなければ、設計ごと変わります。
§7-A は既に `line_users` に行があるLINEアカウントで実施します（§7-A の🔴を参照）。
